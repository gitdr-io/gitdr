## Before you upgrade

git and git-lfs no longer get gitdr's whole environment. Any variable that changed what git does, `GIT_CONFIG_GLOBAL`, `GIT_SSL_NO_VERIFY` or `XDG_CONFIG_HOME` for instance, now has no effect, and gitdr logs a warning as it starts that names each one it found. Put that configuration in `/etc/gitconfig`. The variables git still gets are listed under Security below.

The image installs `/usr/bin/gitdr` owned by root with mode 0711, so the user it runs as can run it and cannot read it. If you install the binary yourself, do the same:

    sudo install -m 0711 -o root -g root gitdr /usr/local/bin/gitdr

The systemd unit and the cron wrapper in `deploy/` changed. Only root reads `/etc/gitdr/gitdr.env` now, `/etc/gitdr` and `config.yaml` belong to root, and every run gets an empty `HOME` of its own. The cron entry runs the wrapper as root, which drops to the gitdr user with `setpriv` from util-linux. On a VM installed from the old samples:

    sudo chown root:root /etc/gitdr/gitdr.env && sudo chmod 0600 /etc/gitdr/gitdr.env
    sudo chown root:gitdr /etc/gitdr /etc/gitdr/config.yaml

then copy the new `gitdr.service`, or the new wrapper and cron entry, as `deploy/README.md` shows. On cron do both together: the old wrapper reads `gitdr.env` as the gitdr user and fails once root owns it.

A drill now writes its report and signature with `destination.retention` on a bucket it confirms immutable, as a backup writes the artifacts. Its key then needs `s3:GetBucketObjectLockConfiguration` and `s3:PutObjectRetention` on S3, as the backup key already does, or `readBucketRetentions` and `writeFileRetentions` on Backblaze B2. Without the first, the report is written as before, with a warning. Without the second, AWS refuses it and the drill exits 3.

gitdr now lists one key before it believes a bucket has no Object Lock, because MinIO gives that same answer about a bucket that does not exist. The listing needs `s3:ListBucket`, or `listFiles` on B2, which the keys in `docs/QUICKSTART.md` have. A key without it gets `unknown` from AWS or MinIO for a bucket with no lock, where it got `not-immutable`.

An artifact over 4 GiB now goes up to S3 in parts. A run stopped in the middle of one leaves its parts behind as an upload that never completes, and AWS bills them as storage. gitdr never aborts an upload, so give the bucket a lifecycle rule that ends incomplete uploads after three days. `docs/QUICKSTART.md` has the rule for AWS and B2. MinIO ends them on its own after a day.

A stopped backup now writes its manifest before it exits, which can take 45 seconds after SIGTERM. Whatever stops gitdr should give it a minute before it kills it. The Helm chart now gives its pod 90 seconds, `terminationGracePeriodSeconds` in its values.

On Azure, `account` has to be a storage account name, 3 to 24 lowercase letters and digits. With `subscriptionID` and `resourceGroup` set, the blob endpoint also has to be the account's own in Azure's public cloud, which is `https://<account>.blob.core.windows.net/`, its `privatelink` name or its Azure DNS zone endpoint, or else an emulator on the same machine. Anything else stops gitdr at startup, since a lock read off another account's container would be reported as protecting this one.

## Reruns and resume

A same-day rerun skips a repository only when a manifest records a complete copy of it under that date. A copy that was only partly written fails the repository by name, with an error that starts `an incomplete copy for <date> exists`. Its keys are create-only, so the next copy is made the next UTC day. Until now any bundle under the date counted, so a copy missing its checksum, metadata or LFS archive was reported as backed up and the run exited 0.

Nothing is written for a repository until all of it has been read and prepared. A failure before that, a token that expires during the LFS fetch for instance, leaves nothing under the date, and the same day's rerun copies the repository cleanly.

A run files every copy under the UTC date it started. One that crossed midnight used to file the later repositories under the next date, where a restore by date did not look.

The next run reads the recent manifests to decide what to skip, so a backup of one repository no longer makes the next full run copy all the others. It believes only a manifest that verifies with its own signing key, which means the first run after a key rotation copies every repository once.

Backup, verify, restore and drill read a manifest of up to 128 MiB, about 1.5 million refs. The limit was 32 MiB, and verify had none. A manifest the next run passes over for its size is named in a warning. A repository's error keeps only the last 64 KiB of git's output, so one noisy clone can no longer make a manifest too big to read.

A same-day rerun no longer fails a repository with no commits. A GitHub repository with issues or pull requests turned off backs up, where every run used to fail it, and its metadata names what was off in a new `unavailable` object. Restore by date takes a bundle only from a repository its run copied in full, as `restore --manifest` already did.

## Rate limits and deadlines

gitdr now waits out GitHub's rate limits. A request refused for the primary limit waits for the reset GitHub names, and one refused for a secondary limit waits its `Retry-After`. When GitHub names no time the waits are 1, 2, 4, 8 and 16 minutes, and a request still refused after five waits fails. A 5xx is tried four times. `source.github.maxRateLimitWait` (`GITDR_SOURCE_GITHUB_MAXRATELIMITWAIT`, one hour by default) caps how long one run spends waiting. A wait that would go past it, or past the run's deadline, is not started, and the request fails with the reset in its error.

The metadata is fetched before the clone, so waiting holds no disk. On GitHub, a rate limit gitdr could not wait out, or a 5xx that outlasted its retries, fails the repository with nothing stored, and the next run tries again. Any other metadata failure, and any on GitLab, stores the code and then fails the repository. Up to v0.1.20 a rate limit left a locked bundle behind with no metadata and no checksum.

`gitdr backup --deadline <RFC 3339 time>`, or `GITDR_DEADLINE`, stops the run's work at that time. Repositories still in progress or not yet reached fail with the deadline as their error. The manifest is written after that, so leave a minute between the deadline and anything that kills the process.

A backup stopped by SIGTERM, SIGINT or its deadline starts no more repositories and stops the ones in flight. Each repository it did not finish is `failed`, with an error that starts `stopped before it finished`, and the run writes its manifest and exits 1. The copies it finished are in that manifest, so verify, restore and drill reach them and a rerun skips them. A stopped run used to file nothing.

## Large repositories

On S3 an artifact over 4 GiB goes up in parts, because a single PUT stops at 5 GiB on AWS, B2, R2 and Wasabi. It is create-only like any other write, and gitdr checks the key before it sends anything. `destination.s3.multipartThreshold` and `destination.s3.partSize` move the threshold and the smallest part, so a test can write in parts without writing gigabytes.

On Azure a blob over 48.8 GiB used to fail after all of it had been sent, and now goes up in larger blocks. MinIO over TLS now takes objects over 16 MiB.

git now runs with limits on its threads and pack memory, which no git configuration file overrides. Bundling a 6 GiB pack went from 3.7 GiB resident to 265 MiB, and cloning large files on 14 CPUs from 1 GiB to 297 MiB. What git fetches and bundles is the same.

A repository takes less scratch disk while it is copied. Its LFS objects leave the disk as they go into their archive, and the mirror goes once the bundle is written. With encryption on, the plain file goes once the encrypted one exists.

A write whose answer was lost no longer fails on its own retry. gitdr asks the store, and when the object at the key has this write's size and CRC32, the write counts.

## WORM checks

A bucket that does not exist now stops a backup at the WORM check, before anything is cloned, and the run exits 1 with or without `--require-worm`. It used to warn, clone every repository and fail each one at its first upload. Nothing is written, so `--output json` prints nothing, as when `--require-worm` refuses a bucket. A Cloudflare R2 token scoped to buckets answers `AccessDenied` about a missing bucket, so on R2 the run still fails at the first write.

An answer that is not S3's, a web page or an empty body for instance, reads `unknown` where it read `not-immutable`, and an object's retention reads `not-checked` where it read `absent`.

On a bucket it confirmed immutable, gitdr checks that the smallest and the largest object a run wrote hold their lock, so a single PUT and an upload in parts are both checked. It used to check the first object only. B2's answer about an object with no lock reads `absent`. It read `not-checked`, and `--require-worm` passed it.

On GCS and Azure the manifest now names the bucket or container and records Azure blob sizes. `wormMode` is left out there, since gitdr sets a mode only on S3.

An unchanged repository is skipped only while its copy is younger than a third of its lock, and never past 30 days. On GCS and Azure that lock is the bucket's own period when it is shorter than `retention.days`, so with a one-day lock a daily schedule copies every repository every day. Up to v0.1.20 a copy there could be relied on after its lock had ended. The first run after the upgrade may copy repositories it used to skip.

Drill reports are locked like the artifacts now. They used to get no retention of their own, so a bucket without a default rule kept them unlocked beside the copies they prove.

## doctor

`gitdr doctor --only destination` checks the bucket alone. It reads only the destination block, so the config needs no source and the machine needs no git, and a bucket can be checked before anything is connected to it.

    gitdr doctor --config config.yaml --only destination --output json

doctor gives up after 45 seconds, or the `--timeout` you give it, and a check that ran out of time says so. A bucket that does not exist fails the `worm` check, and doctor exits 1. A lock that has ended reads `lapsed`, and on Azure a credential gitdr could not get reads `no-credentials`. The store's own error text no longer reaches stdout. doctor names the error by its code there, and the text goes to stderr.

## Security

From gitdr's environment, git and git-lfs get only `PATH`, `HOME`, `TMPDIR`, the proxy variables (`HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY` and `NO_PROXY`, in either case), the CA variables (`SSL_CERT_FILE`, `SSL_CERT_DIR`, `GIT_SSL_CAINFO` and `GIT_SSL_CAPATH`), and `GIT_HTTP_LOW_SPEED_LIMIT` and `GIT_HTTP_LOW_SPEED_TIME`. A secret in gitdr's environment never reaches them. git's messages are in English whatever the locale.

The kernel starts a program its user cannot read as non-dumpable, so with the binary at 0711, git, which runs as the same user, cannot read gitdr's environment or memory. gitdr also makes itself non-dumpable as it starts, which covers a readable binary from then on.

gitdr takes its own secrets out of its environment once it has read them, so an AWS `credential_process` or the Azure CLI, which the cloud SDKs start, no longer sees `GITDR_MANIFEST_SIGNING_KEY` and the rest. git can still read any file gitdr's user can, so give keys in the environment rather than as files.

## Output and the manifest

The manifest stays `gitdr.manifest/v5`, with no field added or removed. Some values changed, and SPEC.md has a note on each.

- An answer that is not S3's gives `unknown` and `not-checked` where it gave `not-immutable` and `absent`.
- `retentionObserved` covers the smallest and the largest object a run wrote.
- On GCS and Azure, `destination.bucket` names the bucket or container, `wormMode` is absent, and an artifact's `size` on Azure is the blob's.
- `already backed up for this date` now means a manifest records a complete copy, and the skip carries that copy's `refs` and `copiedAt`.
- `repos[].error` keeps at most the last 64 KiB of git's output.
- A write settled after a lost answer records the `retainUntil` the store shows, or `0001-01-01T00:00:00Z` when it shows none.

`doctor --output json` now prints a `gitdr.doctor/v1` document. It adds `schema`, then `verdict`, `mode` and `code` on the `worm` check and `observed` on the `retention` check. Every key an older reader used is where it was, and `ok` and the exit code mean what they did, so a bucket that locks nothing still passes unless `worm.require` is set. To learn what a bucket locks, read `verdict`. A config that cannot be read still gets a document, with one failed `config` check.

`backup` logs `repos selected` before the first repository, `repo finished` as each one finishes, and `manifest written` once the manifest is stored. The first two are new, and these three lines on stderr are now part of the contract. A `repo finished` line says what the manifest will record for that repository, and holds only once `manifest written` follows.

`gitdr.meta/v1` gains an optional `unavailable` object. `gitdr.drill/v1` and the JSON that backup, verify, restore and drill print keep their shape.
