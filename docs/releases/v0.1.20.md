## Before you upgrade

Every restore now reads the restored files back and fails if any of them is still a git-lfs pointer. The check doesn't need git-lfs. A backup taken with `backup.lfs: false`, or where git-lfs wasn't installed, holds no LFS objects, and until now its restore and its drill passed with 130-byte pointers where those files should be. They now fail and say the content was not backed up. The restored tree still lands in `--out`. Turn LFS on, install git-lfs where the backup runs, and take a new backup. A repository that keeps pointer files as ordinary text, git-lfs test fixtures for instance, fails the same way.

A GitLab run whose projects sit in more than one namespace now files its manifest under the deepest group that holds all of them, or under `{host}/manifests/` when they share none. It used to go under whichever namespace GitLab listed first. A run whose repositories all sit in one namespace, which includes every GitHub run, files it where it always did.

- The first such run after the upgrade may not find the previous manifest. It then copies every repository once instead of skipping the unchanged ones.
- `gitdr drill` without `--manifest` reads the newest manifest under `--owner`. If a scheduled drill names the namespace the manifests used to go under, it keeps drilling the last run from before the upgrade. Set `--owner` to the shared group, or pass `--manifest`. A manifest filed under `{host}/manifests/` can be drilled only with `--manifest`.

git now gives up on a transfer that moves under 1000 bytes a second for ten minutes. The clone is retried, then the repository fails and the run exits 1. A slow link that needs more room can set git's own `GIT_HTTP_LOW_SPEED_LIMIT` and `GIT_HTTP_LOW_SPEED_TIME`, which override both values.

Drill, restore and backup now refuse a manifest that isn't named for its own `finishedAt`, and any document whose schema doesn't start with `gitdr.manifest/`, a drill report for instance. Every manifest gitdr has written passes, so what gets turned away is a copy stored under another name, or something that is not a manifest. A drill or `restore --manifest` handed one exits 1, a restore searching by date skips it with a warning, and a backup warns and copies every repository. Picking the newest manifest also skips names later than the current time, and anything not filed directly in that `manifests/` directory.

`restore --date` has to be a real date in the form YYYY-MM-DD. Anything else exits 2 before the restore starts. No other form ever matched a backup.

## New

`restore --manifest` restores a repository from the run a manifest records, by the key `backup` prints as `manifestKey`. It needs the public key. The host and date come from the manifest, so `--host` and `--date` are refused next to it. A repository a drill passed restores this way with the drilled manifest's key, exactly as the drill restored it. A repository the run skipped as unchanged has no copy in that run, so restore it with the manifest of the run that made the copy.

    gitdr restore --config config.yaml --manifest <manifest-key> --repo acme/platform/api --out ./restore/api

`--repo` splits at the last slash, so `acme/platform/api` is the project `api` in the GitLab group `acme/platform`. A project in a subgroup could not be restored before.

Without `--manifest`, restore looks for the run's manifest in the repository's namespace, then each namespace above it, then `{host}/manifests/`, among runs that finished on `--date` or the next day in UTC. A run that crossed midnight UTC, or filed its manifest under a parent group, is found now. A drill no longer fails a repository because that search could not find its manifest.

`source.github.tokenPath` (`GITDR_SOURCE_GITHUB_TOKENPATH`) names a file holding a GitHub App installation token, so a backup can run without the App's private key. gitdr reads the file again before every GitHub request and git command, so whoever writes it can swap in a fresh token during the run. Set the token file or the App key, never both.
